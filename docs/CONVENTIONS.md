# 代码规范（通用）

> 本文件只写"写代码时长期成立、不随目录调整而失效"的约定。
> 目录地图、入口清单、命令、存储位置、坑清单属于**项目事实**，由 `README.md`、[`ARCHITECTURE.md`](ARCHITECTURE.md)、[`TESTING.md`](TESTING.md) 维护。
> 刻意不写具体文件路径与命令：结构变了不需要改这里，只有"约定"变了才改。
> 权威顺序：**代码与配置 > 本文档 > 口头约定**。文档与代码冲突时以代码为准，并先修项目文档。

## 1 分层与依赖

- 四层：**视图**（渲染与交互）、**流程与纯逻辑**（无 UI 的计算与编排）、**状态与持久化**、**系统与 IO**（文件、数据库、进程、平台能力）。
- 依赖单向：视图 → 流程/状态 → 系统。低层不得 import 视图，也不直接操作 UI。
- 一个能力只有一个入口；新逻辑挂在既有入口上，不复制第二套。入口以项目文档为准。
- 副作用集中：读取、写入、系统调用不散落在渲染代码里。
- 跨层数据用显式结构传递（对象/数组），不靠全局变量或隐式约定。

## 2 命名

- 文件：组件 `PascalCase`，模块 `camelCase`，系统层模块 `snake_case`（跟随宿主语言惯例）。
- 组件：可复用组件声明自身名称；props 小驼峰、类型明确、默认值给全。
- 状态：`useXxx`；state 用名词，action 用动词（`load` / `persist` / `toggleX` / `setX`）。
- 函数：`openX` / `getX` / `scanX` / `ensureX`；布尔用 `xxxOpen`、`loaded`、`searching`；集合用复数。
- 跨层命名风格转换（snake_case ↔ camelCase）只在一处做，不手工逐字段拼。
- CSS 类 kebab-case；组件块 `.block`，修饰 `.block--modifier`。

## 3 组件

- 块顺序：文件头注释 → `<script setup>` → `<template>` → `<style scoped>`。
- 只用组合式 API，不混 Options API；未启用 TypeScript 时不为局部改动引入 TS。
- 自动导入生效时不要手补 import 来掩盖"未定义"错误，先确认它是否已在自动导入范围内。
- 图标与基础控件走统一的组件与设计系统，不引第二套 UI/图标库，不用 emoji 当图标。
- 组件只负责"这一屏"；跨屏流程、共享逻辑下沉到流程层。
- 事件与状态变更走显式方法/事件，不隐式修改父级数据。

## 4 样式

- 颜色、阴影、圆角、动效走主题令牌；组件样式禁止散落硬编码色值。
- 新增令牌必须两套主题（浅色/深色）同时成立。
- 页面私有样式 scoped；两处以上复用才提取为共享样式。
- 输入方式（触屏/鼠标）与响应式差异用 CSS 媒体查询处理，不靠 JS 判断设备。
- 不新增字体与图标资源，除非设计系统一并更新。

## 5 状态与持久化

- 状态分三类：**会话态**（不落盘）、**偏好**（小、键值）、**领域数据**（结构化、可查询）。按体量与查询需求选存储，不按"哪个方便"。
- 每个存储只有一个写入口；组件不直接读写存储，走 action 或服务层。
- 新增字段三步：**声明 → 加载时白名单校验（类型与取值）→ 保存时显式列出**。漏写保存字段等于重启丢失。
- 字段改名保留兼容读取分支，注释写清弃用条件与移除时点。
- 一致性优先于写入次数：需要时用批量、debounce、事务，而不是每次操作都整存。

## 6 前后端边界（IPC）

- 一次 IPC 对应一个领域动作；参数 camelCase、返回结构稳定，改动同步前端与文档。
- 热路径与批量必须合并请求，并在封装层完成；页面不直接拼装批量协议。
- 失败返回结构化错误；前端必须恢复 UI（`finally`），用户文案本地化，原始错误进日志。
- 新命令闭环四步：**实现 → 注册 → 封装 → 调用**。缺任一步视为未完成。
- 大二进制走二进制响应，不用 base64 或 JSON 数组。
- 新命令若需要在浏览器 mock 下走通，同步补 mock 实现。

## 7 系统层

- 按域拆分模块；命令/入口层只做参数解包，逻辑进可单独测试的函数。
- 锁、事务、连接统一走既有 helper，不在入口里手写。
- 错误统一 `Result<T, E>` 风格并带上下文前缀；不吞错误、不静默降级。
- 外部输入默认不可信：id、路径、文件名白名单校验，拒绝路径穿越。
- schema 变更只追加迁移，不改历史条目与历史 SQL。
- 日志带模块前缀；测试与实现同文件；缺外部资源时打印后跳过，不让测试红。

## 8 注释与文档

- 注释解释 why：意图、外部约束、非显然取舍与风险边界；不复述代码。
- 模块头注释写"为什么存在、谁必须走它"。
- 公共契约写参数、返回、副作用、错误与前置条件。
- 坑与风险写进项目文档的清单，不留在聊天与提交说明里。
- 行为、命令、配置、公共契约变化时同步文档。

## 9 验证

- 先跑与改动最相关的最小验证，再按风险扩大到类型检查、lint、单测、集成。
- 修 bug：先复现，再修复，再补回归。
- 不擅自引入仓库尚未配置的工具链；要加先单独说明收益与成本。
- 无法验证时说明原因与可执行命令，不说"应该可以"。

## 10 禁止

1. 复制既有入口逻辑（另起一套 id 计算、路由拼装、缓存或索引）。
2. 手改生成文件（类型声明、锁文件等由工具产出的内容）。
3. 把调试开关、调试端口写进发布配置。
4. 未说明必要性就新增生产依赖。
5. 提交构建产物、大二进制、日志与测试残留。
6. 为单点需求加抽象层、双路径或配置项——先确认既有入口不能复用。

## 11 提交

- 一次提交只做一件事；说明写"为什么"，不写"改了哪些文件"。
- 中文 Conventional Commits（`feat` / `fix` / `refactor` / `chore`），范围可选。

## 12 提交前自查

- 新代码挂在既有入口上了吗？有没有复制第二套？
- 分层与依赖方向对吗？副作用是否落在非视图层？
- 颜色与图标走设计系统了吗？两套主题还成立吗？
- 新状态字段完成"声明 → 校验 → 保存"闭环了吗？旧字段兼容了吗？
- 新命令完成"实现 → 注册 → 封装 → 调用"闭环了吗？失败了 UI 会恢复吗？
- 跑过与改动对应的最小验证了吗？
